### Google Sheet two-way sync (added 2026-11-18, per user request 「改做雙向同步，Space 同 Sheet 兩邊改都得」)
**Used by**: `syncNow` action (full reconciliation) and every mutating action (immediate write-through), via the privileged handlers in `server/src/privileged.ts`, which shell out to `hatch_gws_cli sheets ...` under the user's connected Google Sheets account. The client also triggers one `syncNow` automatically on page open.
**Source**: Spreadsheet `倉庫存貨 - Demo Co.`, ID `DEMO_WAREHOUSE_SHEET_ID`, URL https://docs.google.com/spreadsheets/d/DEMO_WAREHOUSE_SHEET_ID/edit — created earlier the same day by exporting this Space's 76 items and 63 movements verbatim (Sheet1 tab: 13 columns ID／來源貨單／英文名／中文名／包裝／規格／貨號／條碼／數量／單位／儲存／低存量提示／備註／最後更新；出入記錄 tab: ID／日期／貨品ID／貨品／變動／種類／備註）. That exact column layout is the sync contract.
**Test command**: `hatch_gws_cli sheets spreadsheets get` + `values get` on both tabs before building — structure and values verified (77 item rows incl. header, 64 movement rows incl. header; fractional quantities and the leading-zero barcode `065717034311` intact).
**Stock-code rule (user, 2026-11-18)**: A stock code is exactly 7 characters; anything longer or shorter is blanked, never guessed or passed through. Enforced in `normalizeStockCode` on every path — Sheet parsing (with the blanked row written back so the Sheet cell is cleaned too), Space add/edit actions, delivery-order seed/import actions, and as a backstop in every row written to the Sheet; the Space edit form also blocks saving with a plain-language correction. Existing-data scan found exactly one violation: item 1 第一家 春卷皮 carried the 8-character `10326558` from the original order transcription; the first sync under this rule blanks it in both the Space database and the Sheet.
**Sync rules**: Items were originally matched by the ID column; since the 2026-11-18 Key change (see below) they are matched by the 貨品編號 Key, with the ID column as fallback for blank/invalid code cells. Space mutations write their row (and any new movement rows) to the Sheet immediately; if that write fails the row is flagged `sheet_dirty` and the user is told, and the next sync pushes it instead of overwriting it. On pull, a clean row takes the newer side by timestamp (Sheet 最後更新 vs local updated_at; equal timestamps with different values → Sheet wins, since Space pushes always stamp both). Clean local rows missing from the Sheet count as deleted in the Sheet and are removed; Space deletions are tombstoned in `sync_meta` until the Sheet row is confirmed gone. Brand-new Sheet rows without an ID are imported with the next free ID and the full row is written back. Movements merge by ID in both directions and are never deleted. Storage/unit/kind cells accept both the English codes the Space writes and the Chinese labels （冷凍／乾貨／入貨／出貨 …).

### Stock code as Key + TMP placeholders (added 2026-11-18, per user request 「改做貨品編號做Key，都未掃到貨品編號嘅時候…用 TMP-001、TMP-002 呢種臨時代號」)
**Context**: The user noted 第一家 春卷皮 comes in four sizes — same product name, different sizes — so items are now identified by their 貨品編號 (stock code) as the unique Key, with packing/size distinguishing variants; name alone is never an identity. The user did not specify the other three sizes/packings, so no extra 春卷皮 rows were invented: each further size becomes its own item with its own Key when it is added, exactly like the existing 10"(250mm) row (3 Case).
**Rules**: A real code is exactly 7 characters (unchanged rule); a TMP placeholder (`TMP-001`, `TMP-002`, …, allocated sequentially from a never-reused counter in `sync_meta`) is also a valid Key. No item stays keyless: Space add/edit with a blank code allocates the next TMP; clearing the code on edit allocates a fresh TMP; a duplicate Key is rejected in Space add/edit. Sync (`runSync`) matches Sheet rows to items by the code column first, falling back to the ID cell only for rows whose code cell is blank/invalid; new Sheet rows without a valid code are imported with a TMP Key and the full row (ID + TMP) is written back. `pushItemChanges` locates a Sheet row by ID or by Key.
**Backfill**: `assignTmpCodes` post-submit action runs `ensureItemKeys` once: the 21 items that had a blank code (scan on 2026-11-18: IDs 1, 13, 14, 28, 34, 36, 37, 38, 40, 45, 46, 47, 50, 51, 61, 64, 65, 66, 67, 70, 71) receive TMP-001…TMP-021 in item-ID order — 第一家 春卷皮 (10") is TMP-001 — flagged dirty and pushed to the Sheet; if the Sheet write fails they stay dirty and the next sync pushes them. Quantities, movements and real codes are untouched.

## Long-term data behavior
- **Refresh policy**: Two-way sync with the Google Sheet above — write-through on every Space mutation, plus a full reconciliation on page open and on demand via the 「立即同步」 button. No scheduled refresh; if Google Sheets is unreachable the Space keeps working from its local copy and reports the sync failure.
- **Growth**: Items grow as the user adds new SKUs; every quantity change appends a movement row (入貨/出貨/盤點調整/期初) so history is preserved.
- **Ordering**: Items keep the delivery-order line order via a sort_order column; new items append at the end. Movements list newest first.
- **Time semantics**: Movement timestamps are creation instants stored as timestamp_ms and rendered viewer-local (America/Winnipeg). The source order date (Nov 18, 2026) is stored as plain reference text, not an event instant.

### Shelf status (added 2026-11-18, per user request 「每件貨可唔可以幫我加多個狀態？我想見到貨架空，然後mark低佢要喺貨倉度拎出嚟加貨」)
**Meaning**: Separate from the warehouse quantity — the user works the shop shelf: when a shelf is seen empty they mark the item 貨架空， and when it has to be pulled from the warehouse to refill the shelf they mark it 要補貨； after refilling they tap 已補好 to clear it back to normal.
**Storage**: New `shelf_status` column on `items` (migration 0005), enum `ok` / `shelf_empty` / `need_refill`, default `ok` — every existing item starts at `ok` (no item is pre-marked; the status is set by the user in the UI). Changed via the local-first `setShelfStatus` action (flags `sheet_dirty`, no movement logged, quantity untouched).
**Sheet sync**: The status rides the existing two-way sync as a NEW column N （貨架狀態） appended after the original A:M layout — A:M keep their exact meaning, so nothing already in the Sheet moves. Space writes blank = 正常， `貨架空`, or `要補貨`; parsing also accepts `正常`/`貨架正常`/`空`/`待補貨` and the English codes typed by hand. `runSync` writes the `貨架狀態` header into N1 when it is missing. The UI adds 貨架空／要補貨 badges on item cards, one-tap mark/clear buttons, a 「要補貨」 filter (shows both non-ok states), and a 要補貨 count in the overview strip.

### Low-stock filter includes quantity 0 (fixed 2026-11-18, per user report 「水雲件貨set咗低存量低過二就有提示，但係Filter嗰版睇唔到」)
**Diagnosis**: 永興隆 脆滑雲吞皮（水雲）(stock code 1032570) has `low_stock = 2` and `quantity = 0`. The client's `isLow` required `quantity > 0`, so a 0-quantity item never counted as low — it only appeared under the 缺貨 filter, never under 低存量， and the overview low count excluded it too (`else if`).
**Rule now**: Low means `low_stock` is set and `quantity <= low_stock`, with no lower bound — 0 is below the threshold, so the item shows the 低存量 badge (alongside 缺貨 when at 0), appears in the 低存量 filter, and is counted in the overview low count independently of the out-of-stock count. No data or threshold was changed; this is a display/filter fix only.

### Pre-sync before add/edit + sync safety rules (added 2026-11-18, per user request 「加、或者改之前同步一次又有冇得諗」→「好」)
**Trigger**: Items vanished from the Space (TYJ 春卷皮 8.5"/6"/5" 1032551/1032552/1032553, WING'S 韓國鍋貼皮 1209280, plus three colleague-added items) after the Sheet was overwritten by a stale copy, and stock code 1209280 ended up pointing at a different product （思念湯圓）. The user approved both proposed mitigations.
**Pre-sync (client)**: Every add/edit path syncs BEFORE the change and again after saving (the post-save background sync already existed). Opening 新增／編輯／入貨／出貨 runs `syncNow` first (button shows 「同步緊…」), then re-reads the item fresh (`listItems`) so the form/stepper works on the newest quantity and fields; if the item is gone after the sync, the dialog does not open and a plain-language notice says so. Submitting a form, the quantity input, ＋／−, and shelf-status changes each run one more best-effort sync inside their mutation before applying. A failed/offline pre-sync never blocks the edit — it continues on the local copy and the save stays flagged 待同步 (local-first rule unchanged).
**Safety rules (server `runSync`)**: (1) A local item missing from the Sheet is NEVER auto-deleted anymore, clean or dirty — it is kept and written back to the Sheet, counted as `protected_items`; deletion only happens via Space deletion (tombstones). This reverses the old "clean + missing from Sheet = deleted there" rule, deliberately: with two writers on one Sheet, a missing row is ambiguous. (2) Collision guard: a Sheet row matched by Key (or ID fallback) whose English AND Chinese names both differ from the local item is a different product sharing an identifier — both sides are left completely untouched and the collision is returned in `conflicts` (also persisted to `sync_meta` as `last_sync_conflicts` / `last_sync_protected` and surfaced by `getSyncStatus`); two Sheet rows with the same valid Key are likewise flagged, with only the first reconciled. The UI shows conflicts in a red-bordered 「同步安全提示」 panel with the fix (change one side's code, re-sync) and shows the protected count after each sync.
**Not in this change**: Restoring the already-vanished items and finishing the interrupted quantity updates （八吋半 9 / 五吋 6 / 六吋 5 / Wing 圓餃皮 4 / 扁麵・上海麵各 5 / 雙喜雲吞皮 5 / 圓形餃子皮 4) is data work for the main agent via the artifact's actions, not part of this code edit; the new rules stop it happening again but do not resurrect rows by themselves.

### Key-only matching — no ID / row-number identity (fixed 2026-11-18, per user report 「但唔係用貨品編號做Key，但係我見而家係用行數嚟判別邊行有改」)
**Diagnosis (what the user spotted)**: Despite the "stock code is the Key" rule, four places in the sync still decided identity by the ID column or by row position: (1) `runSync` fell back to matching a Sheet row by its ID cell (column A) whenever the Key did not match, so a shifted/misaligned Sheet (the row-81 incident) made the ID cell — effectively "the row that sits there" — decide which item a change belonged to; (2) the pull-update wrote to `WHERE id = <the Sheet row's ID cell>` instead of the Key-matched local item, and re-derived the item's `sort_order` from its Sheet row number on every sync, so moving rows in the Sheet silently reordered/retargeted items; (3) `pushItemChanges` located the Sheet row ID-first (`rowsById.get(id) ?? rowsByKey.get(key)`); (4) deletion tombstones were numeric item IDs matched against the Sheet's ID cell.
**Rule now**: A Sheet row is matched to a Space item ONLY by its 貨品編號 Key (column F). Column A is written as a display value and never read back as identity; a row number is used solely as the physical write address AFTER a Key match, and `sort_order` is the Space's own order (new imports append at the end). Consequences, all deliberate: inserting/deleting/moving rows in the Sheet cannot redirect a change onto another item; a Sheet row whose code cell is blank/invalid matches nothing and is imported as a new item with a TMP Key (it carries no identity to match by); `pushItemChanges` locates rows by Key only (`rowNumberByKey`); deletions are tombstoned by Key (`deleted_item_keys` in `sync_meta`), with pre-existing numeric tombstones honoured only under a double guard (no live item carries that numeric ID AND the row's Key belongs to no live item). One Key-based bridge is kept for a deliberate Key change: `updateItem` records old Key → item in `sync_meta` (`key_renames`) when an item's code is edited (the normal TMP → real-code replacement), so the next sync matches the Sheet row carrying the OLD code to that item by Key and rewrites it with the new code; records are pruned once consumed or obsolete. Movements still merge by their own sequential movement IDs — those identify log entries, not stock items. The sync panel copy now states the rule plainly （只認貨品編號 Key，唔認 ID 欄、唔認行數）.
**Not changed**: No item data, quantities, or Sheet contents were modified by this edit; it changes only how future syncs decide which row a change belongs to. The 52-row misalignment already sitting in the Sheet is still flagged as conflicts and left untouched, as before.

### Sheet ID column removed — 貨品編號 is the Sheet's primary key column (added 2026-11-18, per user request 「拎走佢 A column ID，用貨品編號應該係 column F 做主要」)
**Change**: The items tab's column A (ID) is deleted from the Google Sheet itself, not just ignored. The items tab goes from 14 columns (A:N) to 13 (A:M): A 來源貨單 · B 英文名 · C 中文名 · D 包裝/規格 · E 貨品編號 · F 條碼 · G 數量 · H 單位 · I 儲存 · J 低存量提示 · K 備註 · L 最後更新 · M 貨架狀態. The 貨品編號 — column F in the old layout the user was looking at — lands at column E after the deletion and is the Sheet's primary key column; sync matching was already Key-only, so this removes the last vestige of the ID column. The 出入記錄 (movements) tab is unchanged and keeps its own ID column (movement IDs identify log entries, not items). The Space's internal numeric item IDs still exist locally (movements reference them) but are never written to the Sheet again.
**Code**: New privileged op `deleteSheetColumnA` (deleteDimension COLUMNS, sheetId 0, startIndex 0, endIndex 1, via spreadsheets batchUpdate). Sync layout updated everywhere: read range A1:M1000, `itemToSheetRow` drops the leading ID (13 values), `parseSheetItems` reads no column A (all indices shift −1, stock code 5→4), `rowNumberByKey` reads index 4, row writes target A:M, the 貨架狀態 header check/write moves N1/13 → M1/12. Legacy numeric deletion tombstones (`deleted_item_ids`) are no longer honoured — they named items by the deleted ID column, so nothing safe remains to match them against; Key tombstones are unaffected.
**Migration**: `removeSheetIdColumn` action, run once as the post-submit action. Order matters because the deployed code already parses the NEW layout: (1) it reads the items tab explicitly as A1:N1000 and parses it under the OLD layout, importing any Sheet-only rows into the Space by Key first so the rewrite cannot lose them; (2) deletes column A via `deleteSheetColumnA`; (3) sets the `sheet_id_column_removed` flag in `sync_meta` BEFORE rewriting, so a failure can never re-run the deletion against the new column A （來源貨單） — a second call returns `already_done` and touches nothing; (4) force-rewrites the whole items tab from the Space in the new layout (new header + every item in Space order, leftover tail rows blanked up to the old row count); (5) runs a full sync internally and returns `{status, items_rewritten, conflicts_after}`.
**Pre-migration safety guards**: Until the migration lands, the live Sheet is still old-layout while the code parses new-layout, so `runSync` and `pushItemChanges` refuse to touch the Sheet at all when the items-tab header A1 is still `ID` — `syncNow` converts that into its normal offline result (local data untouched, nothing written). The migration itself also checks the Sheet directly: if A1 already reads 來源貨單， the ID column is already gone and it returns `already_done` without deleting anything, independent of the sync_meta flag.

**Change**: The user moved the 貨品編號 column in the Google Sheet itself from column E to column A. **Code**: `COL.stockCode` 4→0, `sourceRef` 0→1, `nameEn` 1→2, `nameZh` 2→3, `packing` 3→4; `ITEMS_HEADER` and `itemToSheetRow` reordered to match (貨品編號 first). The sync panel copy now states the Key is Sheet column A.
**Safety guard (new)**: Because reading the Sheet under the wrong layout is exactly what previously flooded the Space with TMP duplicates, `runSync` and `pushItemChanges` now refuse to touch the items tab unless header A1 reads 「貨品編號」 (`assertStockCodeInColumnA`) — an A1 of 「來源貨單」 (previous E layout) or 「ID」 (original layout) stops the sync with local data untouched, instead of misreading 來源貨單 as the stock code. **Not changed**: No item data, quantities, or Sheet contents were modified by this edit; it changes only which column the sync treats as the 貨品編號 Key.

### DIRECT mode — sync abolished (changed 2026-11-18, per user request 「好，離線模式可以犧牲，跟住table嘅排位定應該唔會再改。改為直連個table，唔用同步模式」)
**Decision**: The user accepts giving up offline mode; the Sheet's column layout is final and will not change again. The Space no longer keeps a local copy of items/movements and no longer syncs: the Google Sheet IS the database.
**What changed (code)**: `server/src/actions.ts` rewritten. `listItems` / `listMovements` read the Sheet live (items tab A:M under the final layout — A 貨品編號 Key · B 來源貨單 · C 英文名 · D 中文名 · E 包裝/規格 · F 條碼 · G 數量 · H 單位 · I 儲存 · J 低存量提示 · K 備註 · L 最後更新 · M 貨架狀態； movements tab unchanged).
